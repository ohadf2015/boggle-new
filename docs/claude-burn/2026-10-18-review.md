## 1. Curator ratify can pay coins and points twice
`fe-next/app/api/admin/curator-proposals/[id]/ratify/route.ts:43-52, 110-149`

# Review: classroom socket handlers and modules

I found four real issues and two smaller ones. I did not run any of this. The findings come from reading the code, so I note where one rests on something outside the files shown.

## 1. Any student can act as the teacher using an unverified handshake id (auth bypass)
**`fe-next/backend/handlers/classroomSocketAuth.ts:27-31`**, combined with **`classroomGameHandler.ts:242-247`**

- **What breaks:** a student can end the class, start it, switch its mode or change its pressure settings, and create games as the teacher. The same trick lets them join as any other student.
- **Evidence:**
  - `getAuthUserId` falls back to `socket.handshake.auth.authUserId`, which is client-controlled, whenever `verifiedUserId` is missing. It only logs a warning.
  - Every teacher gate compares that value to `game.teacherId`: `classroomGameEndHandler.ts:125`, `classroomGameHandler.ts:91` and `:421`, `classroomGameModeHandler.ts:91`, and `classroomPressureHandler.ts:64`.
  - `getActiveClassroomGames` sends each full `ClassroomGame` record (`...g`, or `scoped`) to any classroom member. That record includes `teacherId`, `players` with their `socketId`s, and the vocabulary list. So a student can read the teacher's UUID from their own classroom's active-games reply.
  - `joinClassroomGame` is exposed the same way. It checks `joinAuthUserId !== joinPayload.userId`, and `joinAuthUserId` can be the spoofed handshake value. A student can therefore join under another student's id.
- **Fix:**
  - Use only `socket.data.verifiedUserId` in `getAuthUserId`, and drop the fallback.
  - If older clients still need it, gate it behind an env flag that is off in production.
  - Send a sanitized projection in `activeClassroomGames`: gameCode, classroomName, teacherName and lessonNames, without `teacherId`, `players` or vocabulary.

## 2. `createClassroomGame` overwrites any existing game record
**`fe-next/backend/modules/classroomGameManager.ts:63-67`**, reached from **`classroomGameHandler.ts:148`**

- **What breaks:** any verified teacher can submit another live game's code. The code is on the projector, so it is easy to get. The create overwrites the victim's record with `teacherId` set to the attacker, an empty `players` list, and status `waiting`. The record has no `endedAt` any more, so an ended code becomes joinable again. The victim loses control of their own class.
- **Evidence:**
  - `createClassroomGame` uses `setex` with no existence check and no `NX`.
  - The handler only checks that the caller teaches *their own* classroom (`resolveClassroomTeacher`). It never checks that the code is free.
- **Fix:** write with `SET key value EX ttl NX`. On failure, emit `classroomGameError`. Allow an idempotent re-create only if the existing record has the same `teacherId` and `classroomId`.

## 3. Teacher-supplied scores are written into XP and progress with no upper bound
**`classroomGameEndHandler.ts:70-74`**, with **`classroomGamePersistence.ts:524-530`**

- **What breaks:** XP is `max(10, floor(score/10))`, so a client-sent `score` of 1e12 awards roughly 1e11 XP through `award_education_xp`. Finding 1 lets a student pick their own score.
