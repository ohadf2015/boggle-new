# Classic MP — Frontend Perf Audit (2026-05-02)

Two stutters investigated:
- **(A)** Lag dragging across tiles to form a word.
- **(B)** Jank in the first ~1s of the MP results page.

---

## (A) Word-selection drag lag

### Hot path (per cell entered while dragging)

1. `components/grid/useGridInteraction.ts:316-318` — `processTouchMove` builds `newDragCells = [...dragCells, newCell]` (allocates new array every step) and calls `setSelectedCells(newDragCells)`.
2. `components/GridComponent.tsx:189` — useEffect with `formedWord` dep fires `onWordChange(formedWord, selectedCellsLength)` after each selection change.
3. `components/game/InGameScreen.tsx:498-501` — `handleWordChange` calls `setFormedWord` + `setLetterCount`. Two setStates per cell entry.
4. InGameScreen re-renders → rebuilds `sharedLayoutProps` literal at `components/game/InGameScreen.tsx:504-564` — fresh object every render, but PortraitLayout is `memo` so per-prop shallow compare runs.
5. PortraitLayout receives changed `formedWord`/`letterCount` → re-renders. All children that aren't memoized/stable re-render.

`★ Insight ─────────────────────────────────────`
- The drag path's React-state write happens once per *cell entered*, not once per pointermove (pointer-stationary moves early-return at useGridInteraction.ts:292). So the cost is bounded — but the *fanout* of that one write is what hurts.
- The selection-count-clamping trick at GridComponent.tsx:354 (`hasAnySelection = 0 | 1`) keeps non-selected cells from re-rendering on each letter add. So cell-level fanout inside the grid is already optimized — the lag is upstream/sibling, not in the cells.
`─────────────────────────────────────────────────`

### Root causes — ranked

**HIGH — H1. PortraitLayout re-renders on every cell entered.**
`formedWord` lives in InGameScreen and is propagated as a prop to PortraitLayout. PortraitLayout is `memo` but it does receive a changed `formedWord` prop per cell, so it actually re-renders. Each re-render touches:
- `playerAvatars` useMemo — recomputes only when leaderboard changes, OK.
- `compactLeaderboardPlayers` useMemo at `components/game/in-game/components/PortraitLayout.tsx:246` — recomputes only when `leaderboard/username/isTypingMode` change, OK.
- `comboGlow` string ternary, fine.
- Renders: `DynamicEnergyBackground`, `GameOverlays`, `GameHeader` (×2), `CircularTimer` (×4 size variants — all rendered, hidden via Tailwind), `WordFormingArea`, `LeadChangeBanner`, `ComboDisplay`, `ScoreDisplay`, `GridComponent`, `MobileChatFab`, `RoomChat`, `CompactLeaderboard`, `WordsRemaining`, `GameWordList`, possibly `BlastMultiplayerOverlay`, `WordHunt*`. Verify `memo` + stable deps for each.

Fix direction:
- Move `formedWord`/`letterCount` to a tiny dedicated store (Zustand slice or new context) consumed only by `WordFormingArea`. `setFormedWord` then bypasses InGameScreen entirely.
- Or, wrap `WordFormingArea` in a self-subscribing component that reads `formedWord` from a ref/store and don't pass it through PortraitLayout.

**HIGH — H2. Four `CircularTimer` instances render every cell-add.**
`components/game/in-game/components/PortraitLayout.tsx:438-449` renders 4 `CircularTimer` size variants gated by Tailwind responsive `hidden`/`block` classes. They're all in the tree and all re-render on every parent render. `remainingTime` typically only changes once per second, but they re-render at the cadence of word-drag (much higher).

Fix direction: Render exactly one `CircularTimer` based on a `useMediaQuery`-resolved size, or memoize it so it skips render when `remainingTime`/`totalTime` are unchanged. Confirm `CircularTimer` is wrapped in `memo`.

**HIGH — H3. `t()` called per cell during render.**
`components/GridComponent.tsx:523` — `t('game.grid.cellLabel', { row: i + 1, col: j + 1, letter: cell })` runs for every cell every render. With a 4×4 grid that's 16 `t()` calls × 3 regex `replace` passes each at LanguageContext.tsx:330-340 = 48 regex passes per render. Per cell-add this fires.

Fix direction:
- Move the aria-label string into a memoized array keyed by `[grid, language]`.
- Or compute label inside `GridCell` (already `memo`) so the call is skipped when its props are stable.

**MED — H4. `selectedCells.map(...).join('')` runs in a useMemo each render.**
`components/GridComponent.tsx:178` recomputes `formedWord` every selection change — fine — but then a useEffect at line 189 syncs to parent. The double-trip (computed inside grid, then re-set in parent state) is the structural redundancy. Removing the parent state and letting `WordFormingArea` subscribe directly to selection (e.g. via a portal-style "selection store") eliminates step (3) and (4) above entirely.

**MED — H5. `useGridInteraction` rebuilds many handlers per render.**
`comboLevel` is a dep of `processTouchMove` (`components/grid/useGridInteraction.ts:326`). MP receives `comboLevel` as a prop — when combo ticks down/up server-side, all the `useCallback`-wrapped handlers re-create, which re-runs the `useEffect` at line 580 that re-binds the native `touchmove` listener. Re-binding is cheap but it fires often during play.

Fix direction: Read `comboLevel` from a ref so handlers stay stable. Already partially done with `comboLevelRef`; finish wiring it through.

**MED — H6. `OpponentWordFeed` mounted as MP wrapper sibling.**
`components/multiplayer/MultiplayerInGameView.tsx:375` renders `OpponentWordFeed` next to `InGameScreen`. `useOpponentWordFeed` subscribes to socket events for opponent words. MultiplayerInGameView is `memo` so OK, but verify the hook doesn't bubble setState into a parent context.

**LOW — H7. Backend-driven re-renders during drag.**
SocketContext / leaderboard updates from other players land while you're dragging. Whatever `leaderboard` consumer is *not* memoized will re-render mid-drag. Look for inline `.map(...)` arrays passed as props from `app/[locale]/multiplayer/PageClient.tsx` to `MultiplayerInGameView`.

**LOW — H8. Logger/Sentry on missing translation key.**
`contexts/LanguageContext.tsx:321` — `logger.warn` is shipped to Sentry per the project's "never silence symptoms" rule. If any `t()` key in the hot render path is missing in the active locale, every cell-add fires a network-bound log. Verify all `game.grid.cellLabel` etc. keys exist in he/en/sv/ja/es.

## (B) Results page first-second jank

### Mount-time work (in order)

1. `useResultsData` — sorts scores, classifies players. `components/views/ResultsPage.tsx:338`.
2. `useResultsSocketEvents` — registers many socket listeners. `:309`.
3. `useQuickReactions`, `useResultsSideEffects`, `useFirstWinCelebration`, `useCrazyGamesLifecycle`, `useMultiplayerSignupNudge`, `useGameKeyboardShortcuts`. All on mount.
4. **`pickRichestBoardClient` synchronously runs in a `useMemo` during first render** — `components/views/ResultsPage.tsx:545-551`. Calls `generateRandomTable` 6× (default `k=6`) and `scoreBoardHeuristic` 6× before paint.
5. `useEffect` cascade fires post-paint: `setCoinReward`, `setBrainPointsReward`, `setWinStreakData`, `showInterstitial`, `submitLeaderboardScore`, sound effects. Each setState triggers a full ResultsPage re-render — and ResultsPage has many dynamic-imported children that mount+suspend on first paint.

### Root causes — ranked

**HIGH — R1. `pickRichestBoardClient` runs in render at mount.**
`components/views/ResultsPage.tsx:545` — pre-generation of the *next* board for the rematch button blocks the first render of the results page. 6 candidate boards × heuristic scoring on the main thread.

Fix direction:
- Defer with `useEffect` + `requestIdleCallback` (or `setTimeout(0)`) so first paint doesn't pay for it.
- Or move it behind the rematch handler (only generate when host clicks rematch). The board takes <50ms to make even on phones; you don't need it pre-generated.

**HIGH — R2. Coin/XP/streak/cognitive cascade re-renders.**
`hooks/useResultsSideEffects.ts` fires 5+ `useEffect`s on mount, each ending in a `setState`. ResultsPage re-renders 5+ times in the first 200ms. Each render triggers framer-motion entrance children, which is the visible "stutter".

Fix direction:
- Batch the side-effect state with a `useReducer` or single `useState` object — collapse 5 setStates into one.
- Or run them inside `startTransition` so React deprioritizes them under the first paint.
- Move `awardGameCoins` (writes localStorage + dispatches `coinsChanged` event) to `requestIdleCallback`.

**HIGH — R3. CoinContext cascade from `addCoins`.**
The memory note `feedback-coincontext-addcoins-unstable.md` flags `addCoins` as having an unstable ref that cascades through reward hooks. `awardGameCoins → addCoins` runs at mount via R2. CoinContext re-renders → all `useCoins`-consumers re-render under the same paint window.

Fix direction:
- Verify `CoinContext`'s `value` is memoized with stable refs for `addCoins` (use a ref or `useEvent` shim).
- Or split CoinContext into a read-store (state) and write-store (setters) to keep the setter reference stable.

**MED — R4. Many `dynamic(() => import(...), { ssr: false })` children mount on first paint.**
`PostGameEngagement`, `DailyChallengeInvite`, `GlobalRankBadge`, `MultiplayerSignupSheet`, `SignupToast`, `StickyReadyBar`, `PostGameSocialActions`, `WordHuntResultsSummary`, `BlastResultsSummary`, `BlastBoardDomination`, `WheelRushDomination`, `CrazyGamesBanner`, `PostGameWordReview` — each requests a chunk on mount. Network-bound, but each completion triggers a Suspense boundary update + render.

Fix direction:
- Stagger non-critical children behind `useEffect(() => setReady(true), [])` + a 1-frame delay so they don't mount in the same paint as the score reveal.
- Confirm `loading` placeholders are cheap (some have framer-motion entrance which compounds R2).

**MED — R5. Victory/defeat/epic-victory sound on mount.**
`components/views/ResultsPage.tsx:363-380` plays a heavy sample synchronously. If the AudioContext isn't warm, the first `playVictorySound()` call can stall the JS thread for 50-150ms during `decodeAudioData`. This is a known cause of mount-time jank.

Fix direction:
- Decode/precache the result-screen samples during the in-game phase (when the player is already listening to game audio so the AudioContext is hot).

**LOW — R6. `useDeferredValue` is in place for `finalScores` words.**
`components/views/ResultsPage.tsx:502, 542` already defers `allPlayerWords`. Good — no fix needed.

## What to verify next (uncertainties)

- Whether `CircularTimer`, `ComboDisplay`, `ScoreDisplay`, `WordsRemaining`, `CompactLeaderboard`, `RoomChat`, `MobileChatFab` are all wrapped in `memo` with stable prop refs from PortraitLayout.
- Whether `app/[locale]/multiplayer/PageClient.tsx` recreates `leaderboard`/`foundWords` arrays on every parent render (if so, that alone breaks `MultiplayerInGameView` memo).
- Whether `AnchoredNativeBanner` does any layout work during MP play (it's mounted globally per memory note); if so, banner-driven reflow during drag would compound H1.
- Sentry/PostHog event volume during a 3-letter→8-letter drag — quick check of `posthog.capture` calls in the hot path.
- Cost of the global `mousedown` "click outside" listener at `components/grid/useGridInteraction.ts:563`; on each pointer event it does a `gridRef.current.contains(e.target)` test which is cheap but adds up if the rest of the page re-renders the DOM under it.

## Highest-leverage one-line fix

Lift `formedWord`/`letterCount` out of InGameScreen state into a dedicated subscription consumed only by `WordFormingArea`. That single change collapses the per-cell-entry render fanout from "InGameScreen + PortraitLayout + N children" to "WordFormingArea only." Expected drag-lag reduction: substantial on mid-tier Android.
